# Plan for the conference session of 2026-10-27

Aim: turn the desk study into a paper that can be submitted to a robotics or remote sensing conference, with real baselines for the product, and close the gaps an outside reviewer would raise first. Every new analysis is registered in `docs/PREDICTIONS.md` (stages 25 and 26) and pushed before it runs. Anything decided after a result is labelled POST HOC.

Starting point checked before any work: main at 5df2cec, CI green, 93 tests, no tags v1.0 or v1.1 on the remote. The six lidar tiles of stages 12 and 20 are present in `data/raw/lidar/`.

## What a conference reviewer would find missing

An independent audit of the repository on 2026-10-25 (summarised in the list of gaps below) and a second reading with a programme committee in mind gave these gaps, most important first.

| # | Gap | Why a reviewer would reject on it |
|---|---|---|
| C1 | No external baselines. The detector, the map and the planner are compared only with variants of themselves (naive, conservative, risk weighted). | A method paper needs the methods a practitioner would use instead: a slope costmap, terrain roughness indices, interpolation of the coarse model, and a supervised model trained on the same lidar. |
| C2 | The coarse surfaces are block means of the lidar, never a real product. | The operational question is what a rover can learn from a global model such as Copernicus GLO-30, which is older than the lidar and built by a different sensor. |
| C3 | The registered route outcome (an uphill grade over a 3 m baseline) flags most routes of every policy, so it cannot separate methods. | An evaluation endpoint has to measure the hazard the map is meant to see: dune scale slip faces. |
| C4 | No confidence intervals or significance tests for the detector, 40 route pairs per site, spatial autocorrelation ignored. | Differences of a few points of AUC or route failure cannot be read without intervals. |
| C5 | The routes that were scored come from `scripts/planner_lidar.py`, not from the shipped planner. | The product claims have to rest on the product's own code. |
| C6 | No paper in conference format; the manuscript is a long report with 24 stages and no related work section. | A conference paper needs one clear contribution, related work, and six pages. |
| C7 | The default vehicle profile is optimistic (25.5 deg climbing limit against 15.9 deg for the published posterior). | A reviewer will ask how sensitive the planning result is to the vehicle. |
| C8 | Product rough edges: the package version, negative coordinates on the command line, stale statements in the README, CI on one Python version. | Not a reason to reject, but it is what an evaluator meets first. |

Not closable in this session (author or partner): field data, a second human rater, tags, licence, the GitHub Pages switch, any submission.

## Order of work and success criteria

| Order | Workstream | Success criteria |
|---|---|---|
| 1 | Registration | Stages 25 (detection benchmark) and 26 (planning benchmark) written with methods, metrics, statistics and predictions, pushed before any metric is computed. |
| 2 | Data | Copernicus GLO-30 tiles over the six lidar fields fetched with SHA-256 values in the fetch script and the manifest, resampled to the 30 m analysis grids. |
| 3 | Baselines | `src/dunerover/benchmark.py` with the slope, ruggedness, roughness, interpolation, gradient boosting and convolutional baselines, the truth face patches, the metrics and the block bootstrap; unit tests on synthetic surfaces. |
| 4 | Runs | `scripts/benchmark_detection.py` and `scripts/benchmark_planning.py` run once on the registered design; outcomes written in the register; planning uses `dunerover.planner` for the product policies. |
| 5 | Product fixes | Single version source and `--version`; negative coordinates accepted; both climbing limits printed; README headline and stale statements fixed; CI on Python 3.10, 3.12, 3.13 and Windows with an install job. |
| 6 | Paper | `paper/` with an IEEE conference LaTeX source whose numbers and tables are generated from the result files, figures in the project palette, references checked live, PDF built and allow listed. |
| 7 | Review and release | A fresh reviewer reads the paper and the results as a sceptical programme committee member; every finding answered in `docs/REVIEW_2026-10-27.md`; gate and CI green; completeness rescored; release notes 1.2; venue list with deadlines checked live. |

## What is dropped first if time runs short

The convolutional baseline (the gradient boosting baseline is kept), then the Windows CI job, then the vehicle sensitivity run. The review is never skipped.
